# V3 审核规则

默认审核由独立 `app/service.py` 编排，使用 `src/gatekeeper/` 的纯 Python 核心。本文描述实现合同；真实账号、NapCat 能力和生产回执仍需部署验收。

## T/F/I 与分支

- T（`true`）：证据支持条件通过。
- F（`false`）：证据支持条件不通过。
- I（`unknown`）：资料不足、未配置、隐私限制或接口异常。

I 是状态，`ignore` 是动作。T/F/I 分别进入 `on_true`、`on_false`、`on_unknown`，每个分支只能有一个 `next`、`approve`、`reject` 或 `ignore`，可附 `notify_admin`、`log_warn`。T 可被配置为拒绝，I 也可拒绝；反馈必须描述实际情况。

兼容 v2：`all_pass` 有 F 则 F，否则有 I 则 I；`any_pass` 有 T 则 T，否则有 I 则 I。`goto` 保留命名/编号路由；循环或无效路由不能产生未经确认的批准。

## 安全 AST 表达式

新阶段可以使用 `when`，其引用的条件自动成为资料查询依赖。存在 `when` 时，以表达式为准，不再沿用旧 `conditions` 列表。

```yaml
version: 3
groups:
  - id: gate
    name: 粉丝群
    when: "bili_account && no_leave_record && no_conflict && bili_level >= 2 && (follow || medal_level >= 5)"
    on_true: approve
    on_false:
      flow: reject
      reason: 请核对本群入群要求
    on_unknown:
      flow: ignore
      effects: [notify_admin]
```

此格式用于首次管道导入；日常 SQL 备份格式见[配置文档](configuration.md#标准-yaml-导入导出)。

| 写法 | 含义 |
| --- | --- |
| `and`/`&&`、`or`/`||`、`not`/`!`、括号 | Kleene 三值组合 |
| `bili_level >= 2`、`qq_level >= 10`、`medal_level >= 5` | 比较原始已知数值；缺少数值为 I |
| 裸 `bili_level`、`qq_level`、`medal` | 使用群配置门槛计算的 T/F/I |
| `True`、`False`、`None` | 固定 T/F/I |

数值比较也支持 `medal >= 5`，等价于 `medal_level >= 5`；裸 `medal` 仍使用群门槛。数值取全部目标粉丝牌的最高等级；列表不完整时，即使已知某张牌足以证明旧门槛通过，也不把局部等级当作完整最大值，数值比较保持 I。不提供 `guard_level`；粉丝牌不等于当前舰长。禁止函数调用、属性访问、下标、任意代码、运算表达式及未知名称；有长度、节点数和深度上限。

| 运算 | 关键结果 |
| --- | --- |
| 与 | F ∧ I = F；T ∧ I = I |
| 或 | T ∨ I = T；F ∨ I = I |
| 非 | ¬I = I |

## 八项条件

| 条件 | T | F | 常见 I |
| --- | --- | --- | --- |
| `bili_account` | UID/唯一精确昵称及资料确认 | 格式错误、不存在、确定无昵称匹配、多个精确同名、空输入 | 搜索不完整、接口失败、资料缺失 |
| `bili_level` | 达到配置的 B站等级门槛 | 已知等级低于门槛 | 等级未知或门槛未设；数值表达式仍可使用已取得的数值 |
| `qq_level` | 达到 QQ 门槛，0 是有效测得值 | 已知等级低于门槛 | 接口/事件均无法读取，或门槛未设 |
| `follow` | 关注任一目标 UID | 完整证据确认均未关注 | 目标未配、隐私或分页不完整 |
| `medal` | 任一目标粉丝牌达到门槛 | 已确认没有达标牌 | 列表不可读取或字段缺失 |
| `no_leave_record` | 当前群无退群记录 | 当前群有退群记录 | 未提供 QQ 的模拟 |
| `no_conflict` | UID 未归属其他 QQ | UID 已归属其他 QQ | 身份或归属查询未确认 |
| `no_identity_change` | QQ 未更换现有绑定 | 本次 UID 与现有绑定不一致 | 身份、记录或 QQ 未确认 |

多个关注/粉丝牌目标为“满足任意一位”。绑定登记本身不证明账号所有权；需要强一些的证明时启用[所有权挑战](ownership-and-patrol.md)。

## UID/昵称严格单路分流

先提取 QQ 验证问题的答案，再本地分流：

| 输入 | 查询 |
| --- | --- |
| 纯数字、全角数字 | UID 名片 `/x/web-interface/card` |
| `UID:123456`、`B站UID：１２３，４５６` | 清洗标记内容后走 UID 名片 |
| `UID:abc123`、`UID:0` | UID 格式错误，本地拒绝，不尝试搜索 |
| 含字符的昵称，如 `昵称123`、`昵称 带空格` | 用户搜索，要求唯一精确匹配 |
| 未标记的 `123,456` | 作为含符号昵称，不任意提取数字 |

显式 UID 清洗全角、不可见格式字符、外层引号/括号和数字分隔符。UID 当前接受 1–20 位 ASCII 数字，数值范围为 1–9223372036854775807（SQLite 有符号整数范围）；超出时本地提示检查，不发送接口请求。两路不互相回退；不是从一段任意说明中猜出昵称或 UID。

UID 名片中的 `card.name`、昵称搜索唯一匹配的 `uname` 为已确认账号昵称，和申请原文分开处理；审计、绑定、通知与 `/检查bili` 使用接口返回的昵称。仅返回 UID/等级但缺少昵称时不把输入当作昵称，也不因此改变已有资格判断。`/检查qq` 对旧记录中同 UID 的数字或 `UID:` 占位做有界只读补名，保留原始审计、统计和动作状态；接口不可用时显示“未记录”，不伪造昵称。隐私导致的关注/粉丝牌 I 不会因补名变为通过。

真实申请中，未显式标记的纯数字恰好等于申请 QQ 时，本地提示可能误填 QQ，零 B站请求；如数字确为 UID，申请者可明确填写 `UID:数字`。只读模拟没有申请 QQ，不能覆盖此检查。

账号找不到时必须提示检查 UID/完整昵称，并包含“请不要填写B站昵称或UID以外的内容”。风控、网络和不完整搜索仍为 I。其他拒绝见[反馈说明](rejection-feedback.md)。

## B站资料与风险限制

所有 B站请求共享平滑限流；确定的资料结果有短期、有限容量缓存，相同在途查询合并。缓存作用于资料，不替代审核决策、绑定检查或 pending 预约。默认参数及凭证变化见[架构](architecture.md)和[凭证管理](credentials.md)。

共同关注仅在目标前提和分页完整性可确认时用于确定否定。登录账号已关注目标的前提只短暂缓存60秒，过期后重新核验关系并重查共同关注，避免把旧启动状态永久当作证据。当前关注回退无法判断时，UP 视角反查先验证登录 UID 确为目标，再读取该目标的粉丝分页。命中可支持正面结论；只有单目标且完整可解析列表读完才能确定否定，多目标只查了其中一位仍为 I。它不是可绕过所有隐私的后台搜索，也不提供舰长/粉丝牌的 UP 视角证明。社区接口的可用性不是官方承诺。

## 启动与重连补审

后台每 30 秒检查 OneBot 及 QQ 的实际状态；`get_status` 的 `online`、`good` 必须均为 true。首次健康连接、WebSocket 重连、已观察到的 QQ 离线/接口异常后恢复时，读取一次 NapCat `get_group_system_msg(count=100)`。启动时尚未连接或读取失败会在后续周期重试，不要求再次手动重启。此流程不自动重启 NapCat，也不能替代需要人工扫码的 QQ 登录。

仅从 `join_requests` 取 `checked` 严格为 false 的记录；群号、申请 QQ、申请序号必须可精确核对，申请序号须为 JS 安全范围内的正整数，申请原文须为字符串。同群同序号存在多条记录时跳过，邀请、已处理、缺字段或不安全标识不自动审批。仅处理当前已配置且启用的群，使用 `message` 原文进入普通审核：UID/昵称分流、QQ 等级、退群/绑定检查、当前阶段规则和可选所有权验证均保留。

实时事件与补审按 bot、群、add、flag 串行执行整条审核。同意、拒绝、普通忽略均保存原申请键，重连及重启后跳过已记录申请，不重复动作、统计或阶段通知。相同 QQ 的新 flag 是新申请。等待扫码的记录不占用终局申请键，仍允许原有严格扫码恢复流程复核；pending 申请由下述对账处理，补审不重复发送动作。升级前没有申请键的旧忽略记录无法精确关联，可能被补审一次，不通过 QQ 或昵称猜测重复关系。

NapCat 只返回有限系统消息窗口，没有在此接口验证可用的历史翻页。达到 100 条时日志提示较早申请可能需要人工检查；不能把列表缺失当作已处理，也不能承诺覆盖所有历史申请。相同健康连接中完成扫描后不持续重审未通过的旧申请；需要重新审核时应重新申请或走既有人工/扫码恢复流程。

## pending、对账与人工确认

同意/拒绝前先持久化审计意图与精确动作，再调用 OneBot。明确动作失败可记录失败；超时、断线、取消保持 pending，不建立成功绑定。

pending 只预约相关 QQ、B站 UID 与请求，其他身份继续审核。保留 UID 预约可阻止另一个 QQ 在结果未知时抢占；本地数据库写失败仍会停止自动审批以避免丢失意图。

后台对账只有在证据匹配 bot、群、QQ、subtype、flag 和预期结果时才可核销；明确仍未处理才可重发一次，重试预算先落盘。**仅在群内、列表里没有申请、`checked=true` 均不足以确认本次动作。** 旧记录缺精确元数据或持续未知时转人工。

默认 NapCat 适配器先确认原机器人连接与 `get_version_info` 的 NapCat 身份，再读取 `get_group_system_msg(count=100)`。仅当唯一一条 `join_requests` 同时匹配原 flag 的安全整数 `request_id`、申请 QQ 的 `invitor_uin`、群号，并且 `checked` 严格为 false 时，提供“仍未处理”证据。它不把 checked=true 解释为同意/拒绝成功；不匹配、字段缺失、不支持或超大 ID 等语义未知直接交人工。

识别到纯传输超时、断线或原机器人离线时，只重试只读检查：检查次数持久化，按 5/15/45 秒目标退避，第四次仍不可用转人工。实际执行时刻受后台轮询周期影响；默认周期 30 秒，可用 `DECISION_RECONCILE_INTERVAL` 调整。读检查重试不会直接重发审批，外部动作仍必须取得精确“未处理”证据并且最多重发一次。这是协议适配与有界恢复，不保证任意 NapCat 版本可自动恢复。

超级管理员先核对真实 QQ 结果，再用 `/确认审批 <审计ID> applied|failed`，或控制台相应操作。`applied` 表示此前预期动作确已生效，`failed` 表示确认未生效，不是新批准/拒绝命令。

## 模拟与验收

`/检查bili <群号> <UID或昵称>` 不写申请、绑定、退群记录，不发审批或阶段通知；没有 QQ 的条件为 I。它不能代替真实事件 → 审批回执 → 审计/绑定 → 用户反馈的受控验收。
