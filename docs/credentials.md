# B站凭证管理

默认凭证服务为 `app/bilibili/credentials.py`；兼容的手动/CookieCloud 工具在 `credential.py`。当前活动 Cookie、refresh token、generation 和待确认刷新状态属于 SQL 配置，公开快照、普通导出与状态接口隐藏秘密。

## 获取方式

| 方式 | 行为 |
| --- | --- |
| `/设置cookie <Cookie>` 或管理接口 | 将 Cookie 写入 SQL；清除旧 refresh token/刷新中间状态，避免配到其他账号 |
| `/获取cookie` 或管理配置 | 可选 CookieCloud 同步；host、UUID、key 首次从环境导入，之后由 SQL 维护；取得后按手动 Cookie 替换处理 |
| 管理员 `/登录二维码` 或控制台扫码 | 调用网页扫码生成/轮询接口；确认返回账号可登录后自动保存 Cookie 与配对 token |
| 原生刷新 | 有可用 token 和 CSRF 时检查是否需刷新，验证新凭证身份后保存并确认旧 token |

管理员二维码是登录 **Bot 使用的 B站账号**，会替换服务凭证。申请者所有权 H5 的验证流程与之隔离，不能把申请者登录凭证保存成 Bot 活动凭证。

管理员二维码会话约 180 秒，轮询有最小间隔和数量上限；等待扫码、待确认、过期、不可用分别返回状态。不要公开分享管理会话、登录二维码或 token。

## 刷新顺序与失败恢复

1. 用当前 Cookie 确认账号身份。
2. 查询 refresh 状态，获取 refresh CSRF。
3. 请求新 Cookie/token，确认新凭证仍为同一账号。
4. 先原子持久化新凭证、generation 和旧 token 待确认记录。
5. 再确认旧 refresh token；失败保留待确认状态供后台恢复。

网络/API 检查失败不会主动清空当前 Cookie，也不会把“无法确认”说成“已过期”。并发手动修改通过配置版本与凭证 generation 检查保护，过期的刷新结果应丢弃而非覆盖新凭证。

后台刷新循环约每小时执行；没有 Cookie、token 或必要 CSRF 时返回相应状态，不意味着已自动续期。仅有手动 Cookie 不保证存在有效 refresh token；`ac_time_value` 可作为兼容来源。外部刷新接口本身会改变会话，普通只读烟测不应调用。

## 指纹、WBI 与资料缓存

- 缺少 `buvid3`/`buvid4` 时尝试 B站指纹接口，保留已有字段，并记录 `b_nut`；接口取不到的字段不伪造为已获得。
- WBI 使用 nav 中的实时签名密钥和缓存，不能保证服务端风控始终允许请求。
- 全部 B站 HTTP 请求共享平滑限流；凭证相关变化使新查询采用新作用域/缓存失效。
- 健康状态可报告确认时间和凭证摘要；它不返回原 Cookie、refresh token 或刷新待确认秘密。

## 目标关注与通知

服务会在启动、手动 Cookie 生效或目标 UID 修改等路径检查登录账号关注目标的前提，并可能调用关注接口补齐。这会修改登录账号的关注关系；需准备允许该用途的服务账号及 `bili_jct`。失败保留可解释结果，不把未确认前提用于确定否定申请者。

Cookie nav 监控将明确过期与网络/API 异常分开；磁盘与 Cookie 可发送 SMTP 告警。具体去重、环境项和实际送达验收见[邮件告警](cookie-email-alert.md)。

## 协议验收范围

扫码、原生刷新、指纹和资料接口基于可变化的社区协议实现。fixture 测试可以验证顺序、身份匹配、失败恢复和并发保护；不能证明你的账号、IP 或生产环境当前支持这些接口。

只读上线检查包括 nav 登录状态、UID/昵称查询和 OneBot 状态。扫码登录、刷新确认、自动关注以及实际 QQ 消息/审批需独立记录受控验收结果。不存在“自动保活永不失效”或“绝不封号”的保证。
