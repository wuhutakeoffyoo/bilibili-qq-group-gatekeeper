# 2026-10-30 SnowLuma 申请漏收核查

本记录区分上游讨论、原始协议证据、适配器私有修复与业务审核结果。账号、群号、申请原文和原始报文仅保存于生产机私有回执。

## 根因与上游状态

[SnowLuma #597 的补充评论](https://github.com/SnowLuma/SnowLuma/issues/597#issuecomment-6514882164)纠正了最初“未实现主动申请推送”的描述：实现已存在，但读取申请列表时把 OIDB 返回的操作类型当作前端通知类型，再次正向转换，导致主动申请 `1` 变成邀请 `2`，申请人读取了不存在的邀请者字段。实时推送无法匹配，列表的 `requester_uin` 也为 0。

截至本次核查，该 issue 由提交者自行关闭，关闭时间早于上述纠正评论，没有关联修复提交。[旧 PR #382](https://github.com/SnowLuma/SnowLuma/pull/382)也已关闭且未合并；不能把 issue 的关闭状态当作修复发布证据。官方 v2.2.1 发布说明未包含本项修复，本次没有据此升级版本。

生产只读采集同一申请的 UID/UIN 两种 OIDB 响应：二者均为操作类型 `1`、待处理状态 `1`，目标字段能分别精确关联 UID 与申请 QQ；OneBot 修复前却返回类型 `2`、申请人 `0`。因此问题位于适配器转换，不能通过放宽业务解析器、猜测申请 QQ 或接受邀请标识修复。

脚本要求原始摘要和两个替换点完全一致，校验输出摘要，并拒绝覆盖已有文件。不得对其他版本套用。派生镜像以固定基镜像加 `COPY index.mjs /app/runtime/index.mjs` 构建，完整上游运行文件不随仓库分发或公开推送。使用者须遵守 SnowLuma 协议。

生产保留原运行文件、Compose、SQLite 快照和诊断回执。已验证私有镜像内的 Node 语法，以及主动申请、邀请和未知类型分类。运行中的原容器只替换该文件并重载 Node 适配器，QQ 主进程及其登录未重启。Compose 已指向私有镜像，供未来重建使用；本次未重建容器，不能宣称验证了容器重启免登录。

未来升级须先保留此镜像和最新数据，再核对新版本的真实申请类型、申请人和完整 flag；只有官方修复通过同样核验后才移除此私有修复。不要直接拉取同名标签覆盖修复。

## 生产补审结果

- 修复后目标申请恢复为类型 `1`，申请 QQ 与原始报文一致，昵称答案通过搜索路由解析出真实 B站账号。
- 系统列表共 13 条，其中明确未处理主动申请 7 条；已启用群涉及 6 条，其他群不处理。
- 6 条中 5 条精确关联既有“忽略”审计，未重复动作、统计或通知。新增 1 条审计，审计总数从 420 增至 421。
- 新申请的账号、B站等级、QQ 等级及无退群记录均通过；关注因隐私为 Unknown，粉丝牌未达到目标要求，当前群规则最终为“忽略”。此结果不是拒绝或同意回执，没有发送审批动作。
- 原报文中其他已处理或类型不同的历史通知不被改造为主动申请。有限列表之外的历史情况仍须人工核对，不能承诺追回所有遗漏申请。

此前 [10 月 26 日记录](production-acceptance-20261026.md)中的“可补审数量为 0”仅是当时业务解析器的观察，受本缺陷影响，不能证明当时没有待审申请，也不能证明实时主动申请接收已验收。

## 业务兜底与验证边界

业务补审保留每 30 秒状态检查；首次就绪、重连或已观察到的离线恢复立即扫描，健康连接持续运行时也在距离上次成功扫描至少 60 秒后再次读取。运行时调度和接口耗时会影响实际时间，不是严格 60 秒处理承诺。已记录申请依靠持久化原申请键去重；失败下个状态检查周期重试。邀请、零申请人和语义不明的行仍跳过。

回归覆盖健康连接漏推送后的发现、周期失败重试、旧忽略通知去重、收件箱变体及邀请隔离。生产已验证本次真实遗漏申请进入审核并写入记录；未来新申请实时推送、同意/拒绝外部动作、完整容器重启恢复仍需各自证据，不能从“忽略”审计或健康接口推断。
