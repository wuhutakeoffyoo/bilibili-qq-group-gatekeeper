# 所有权挑战、H5 与成员巡检

这两项按群启用，默认关闭。它们不会把所有网络异常变成失败，也不保证绝对所有权、舰长资格或永不触发风控。

## 所有权验证的实际流程

暗号模式（`dm` / `dynamic`）：

1. 群启用验证后，真实入群申请已识别到 UID，但尚无可用证明时，通过拒绝反馈提供专属 HTTPS 验证链接。
2. 链接绑定群、QQ、UID 和有效期；用户使用指定 B站账号发送本次随机码。
3. H5 后端只接受挑战 ID 和秘密，读取 B站返回的真实发送者、时间与内容进行匹配。浏览器不能自行提交“已验证 UID”。
4. 成功后，用户在有效期内用同一 QQ/UID **重新申请**；答案只填写昵称或 UID，不填写随机码。
5. 新申请消费一次证明，并继续执行本群等级、关注、限制名单、绑定和 pending 保护；验证成功不会绕过这些规则。

挑战由真实 QQ 申请发放，公开网页不能任意指定别人的 QQ 创建挑战。任务状态仅存秘密散列；精确反馈、审计与持久动作载荷可能保留完整链接，数据库及备份必须私有。H5 使用片段传递秘密并移除地址栏片段，避免常规访问日志和 Referer 泄漏。链接仍应保密，不要转发。

### 按群设置

将以下对象放入相应 SQL 群配置的 `verification`，通过版本化配置保存：

```json
{
  "enabled": true,
  "mode": "dm",
  "receiver_uid": "12345",
  "public_url": "https://verify.example.com",
  "ttl_seconds": 900
}
```

私信模式要求活动 B站 Cookie 确为 `receiver_uid` 的收信账号。申请者向它发送整行验证码，后端从真实消息读取 sender UID、receiver UID、内容与时间。

动态评论模式示例：

```json
{
  "enabled": true,
  "mode": "dynamic",
  "reply_oid": "123456789",
  "reply_type": 17,
  "dynamic_url": "https://t.bilibili.com/123456789",
  "public_url": "https://verify.example.com",
  "ttl_seconds": 900,
  "max_pages": 5
}
```

`reply_oid` 是实际评论区对象 ID，可能不同于动态 ID；管理员需核对，程序不会猜测。评论分页有上限，未发现证据是等待或不可用，不是证明账号归属失败。当前不自动删除评论。

TTL 限制为 120–3600 秒，默认 900 秒。配置变更、过期、管理员撤销和已消费都会使旧挑战失效；H5 检查间隔至少 5 秒，并有请求速率与大小限制。

### H5 路由与边界

同一个 ASGI 应用提供 `/verify`、`POST /verify/state`、`POST /verify/check`，以及扫码用的 `POST /verify/qr/start`、`POST /verify/qr/poll`。对外仅反向代理所需 H5 路径；管理台另行限制。

### 申请者扫码模式

```json
{"enabled":true,"mode":"qr","public_url":"https://verify.example.com","ttl_seconds":900}
```

该模式将原申请保持未处理，通过申请QQ私聊提供专属链接；私聊明确失败才改用拒绝反馈，要求验证后重新申请。重复事件不会撤销已发送的链接。私聊回执不明确时保留原申请，通知管理员核实。

H5 从 B站原生二维码接口取得临时扫码会话，后端用 nav 验证扫码身份必须等于本次申请 UID。申请者 Cookie/token 不写入 SQL、不替换管理员凭证；内存凭证使用后立即丢弃。二维码会话只绑定当前挑战，跨挑战、错误 UID、过期或重放不能放行。

证明成功后，仅当原机器人连接，且已核对的 SnowLuma 或 NapCat 实现提供精确证据，确认原 flag/群/QQ 仍未处理，才用最新规则重新审核原申请；不是绕过条件的直接同意。迁移前遗留的 NapCat 数字 flag 不会自动通过 SnowLuma 重发。若条件变化，可明确拒绝；审批回执未知则进入正常 pending。原申请状态不明确时不发送审批，证明在有效期内可用于同QQ/UID的新申请；必要时取消当前申请后重新申请或联系管理员。

管理员扫码登录用于替换 Bot 凭证，是另一条受管理会话保护的路径，不能发给申请者。暗号模式已拒绝的原申请不会被网关重新批准。

私信/评论证明仅说明指定账号在挑战有效期内发布了匹配内容；账号共享、转让或主动代操作并非本系统可排除的风险。接口隐藏、不可用、分页未发现、错误发送者和错误时间都不能产生通过证明。

## 成员巡检

巡检只针对 OneBot 当前完整成员列表中的普通成员，且必须匹配本群最近一次已确认批准的 UID 和当前归属，跳过群主、管理员、角色未知和机器人。其他群的绑定和历史 `groups_json` 不作为本群资格依据。

群配置示例：

```json
{
  "enabled": true,
  "mode": "report",
  "when": "follow || medal_level >= 5",
  "interval_seconds": 86400,
  "grace_seconds": 86400,
  "remind_interval": 86400,
  "remind_channel": "group",
  "max_actions_per_run": 5
}
```

将对象放入该群 `patrol`。`enabled` 默认 false；`mode` 可为 `report`、`remind` 或 `kick`。默认间隔调度最小一小时；也可设 `cron` 与 IANA `timezone`，此时按 cron 调度：

```json
{"cron":"0 3 * * 0","timezone":"Asia/Shanghai"}
```

例为该时区周日 03:00。五字段依次分/时/日/月/周，支持 `*`、列表、范围和步进，周日为 0 或 7；同时限制日期和星期时按 OR 匹配。未指定时区默认 `Asia/Shanghai`，不取服务器隐含时区。调度器每20秒检查，同一分钟只安排一次，最多两个并发巡检任务；低优先门控默认每秒 0.2 次，实际 HTTP 仍受全局限流。

必须明确配置 `patrol.when`，支持 `follow`、`medal` 及 `medal_level` 的安全三值表达式，引用群现有目标 UID。未配表达式为未知，不猜测入群规则原本的与/或关系。它不重跑完整入群管道，也不检查舰长到期/guard 等级。错误/隐藏资料参与 I 计算，不能将不确定性当作确定失格。

### 报告与动作

- 可在控制台手动生成报告，即使未启用定时巡检；生成报告本身不发提醒、不踢人。
- 报告绑定策略散列，超过 24 小时或策略变更后不能直接执行。
- `remind` 默认在群内 `@` 提醒；`remind_channel: private` 可改私聊。
- `kick` 必须经过宽限期，默认一天；自动模式至少 60 秒。
- 动作前重新读取成员角色、绑定、pending 和 B站资料；未知或已恢复则跳过。
- 先持久化动作 pending，再调用 OneBot。超时/断线保持未知，不自动重复提醒或踢人；明确失败可记录失败。
- 已执行移除不会重复发送；提醒有最小间隔。通知/移除均是外部写操作，需单独受控验收。
- 每次动作默认最多 5 项，`max_actions_per_run` 限制在 1–50，超过的项跳过。

## 退群绑定策略

群配置 `release_binding_on_leave` 默认 false，保留现有归属。设为 true 时，服务在记录退群后尝试释放，但须确认：

1. 该 QQ/UID 无未确认审批。
2. 能完整查询机器人加入的群和成员。
3. 该 QQ 已不在机器人其他群中。

任何范围不完整或查询异常都保留归属。释放只删除当前 B站归属并记录释放事件，不删除申请审计、历史统计或退群记录。因为 UID 归属是全局的，离开一个群不会直接清掉仍用于其他群的绑定。

## 外部验收

fixture 覆盖时间/发送者/随机码匹配、重放、未知不踢和动作幂等；真实私信/动态可读性、QQ 临时私聊及移除能力须在管理员控制的账号/测试群验证。普通只读烟测不能调用删除评论、发送提醒或踢人。
